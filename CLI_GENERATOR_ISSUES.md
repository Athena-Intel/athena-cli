# `fern-cli-generator` 0.16.4 — known codegen issues

This repo is generated by [`fernapi/fern-cli-generator`](https://github.com/fern-api/cli-sdk)
**0.16.4**, wired into the Fern release pipeline in
[`Athena-Intel/athena-fern-config`](https://github.com/Athena-Intel/athena-fern-config)
(`fern/generators.yml`, group `cli-sdk`).

The generator at 0.16.4 emits Rust that **does not compile as-is**. Three
post-generate fixes are required every time the CLI is regenerated. Because of
this, the `cli-sdk` group runs in `github: mode: pull-request` — a human applies
the fixes below and confirms `cargo build` before merging the generator's PR.
Flip the group to `mode: push` only once these are fixed upstream.

> **Note on command naming:** there is intentionally **no** OpenAPI overlay in
> this pipeline anymore. Command grouping is driven entirely by `x-fern-sdk-*`
> annotations on the public endpoints at the API source
> (`agora/agora/web/api/public/v0/**` in `Athena-Intel/demo-app-monorepo`).
> Any endpoint missing `x-fern-sdk-group-name` / `x-fern-sdk-method-name` gets
> bucketed into a junk top-level `api` command group — fix it at the source,
> not with a local overlay.

`cli/athena/custom.rs` is protected by `.fernignore` and is never overwritten.

---

## Issue 1 — `reqwest` `multipart` feature not enabled

**Symptom:** `athena-types` fails to compile; the generated multipart form code
references `reqwest::multipart::*` but the crate's `multipart` feature is off.

**Fix:** in `athena-types/Cargo.toml`, enable the feature:

```toml
reqwest = { version = "0.12", features = ["multipart"], default-features = false }
```

The generator should add the `multipart` feature whenever it emits multipart
request bodies (the file-upload endpoints).

---

## Issue 2 — generated request-type module not registered in `types/mod.rs`

**Symptom:** the generator writes a request-model file under
`athena-types/src/types/` but does not always add the matching `pub mod` /
`pub use` lines to `athena-types/src/types/mod.rs`, leaving an orphaned,
unreferenced module (and, conversely, a missing re-export for code that needs
the type).

**Fix:** for each newly generated `athena-types/src/types/<name>.rs`, ensure
`mod.rs` has both:

```rust
pub mod <name>;
pub use <name>::<TypeName>;
```

Diff `git status` after `fern generate` for untracked `types/*.rs` files and
confirm each is registered. Build to surface any unresolved-import errors.

---

## Issue 3 — `sdk_glue.rs` `sdk_client()` client tree is malformed

**Symptom:** the generated `cli/athena/sdk_glue.rs` `sdk_client()` constructor
does not match the SDK's actual `ApiClient` shape:

- it adds a stray top-level `http_client` field to `ApiClient` that the struct
  does not have, and
- it omits sub-clients — both top-level resource clients (e.g. `users`) and the
  nested children under grouped resources (`agents.{drive,general,research,sql}`,
  `tools.{calendar,email,sheets,structured_data_extractor,tasks}`).

**Fix:** hand-build the full nested tree so it mirrors
`athena_sdk::api::ApiClient` exactly. See the committed `cli/athena/sdk_glue.rs`
for the current correct shape; re-sync it with the SDK whenever resources or
sub-clients are added/renamed (the `athena-sdk/src/api/resources/` tree is the
source of truth).

## Regeneration checklist

After a `fern generate` (or reviewing the generator's PR):

1. [ ] `athena-types/Cargo.toml` — `reqwest` has `features = ["multipart"]` (Issue 1).
2. [ ] Every new `athena-types/src/types/*.rs` is registered in `types/mod.rs` (Issue 2).
3. [ ] `cli/athena/sdk_glue.rs` `sdk_client()` matches `athena_sdk::api::ApiClient` — no stray `http_client`, all sub-clients present (Issue 3).
4. [ ] `cargo build` succeeds.
5. [ ] `cargo build --no-default-features --features rustls` succeeds (distribution TLS backend).
6. [ ] `cli/athena/custom.rs` still compiles against any renamed SDK methods/sub-clients.

## Upstream

These are `fern-cli-generator` bugs, not configuration problems on our side.
File/track them against https://github.com/fern-api/cli-sdk and remove the
corresponding step here once a fixed generator version is pinned in
`athena-fern-config`'s `fern/generators.yml`.
